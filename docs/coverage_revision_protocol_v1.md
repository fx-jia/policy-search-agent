# 固定证据的子问覆盖复查：开发诊断协议 v1

日期：2026-09-22。用户已同意尝试“先检查子问漏答，再考虑补检索”。本轮是现有生成评测流程中的有限改动，不改生产默认方案。

## 假设与对照

证据已进入上下文但answer遗漏子问时，第二次调用按子问逐项检查，可能补全回答。核心对照是相同两次生成预算下，**子问覆盖复查 vs 普通复查**；直接生成初稿是额外的单次调用参照。

每题先生成一份共同初稿，再分别交给两个独立复查分支。两个分支看到相同原问题、相同证据和同一初稿，互不看到对方输出。普通复查检查正确性、完整性、相关性和引用；子问复查显式从题干拆待答事项，逐项检查answer而非只看claims，必要时据原证据补正，最终统一作答。coverage记录题干连续短语、覆盖状态、E编号，只是模型自报，不是真值。

这是生成阶段的检查与修订，尚未做子问检索、query改写或多份独立答案合并。与此前失败的单次parts输出不同：本次增加一轮修订，并设置等调用次数的普通复查对照。

## 冻结输入与预算

复用policy_qa_v1的10道开发诊断题及45个已脱敏审核片段，题序不变。每题候选来自已保存的Dense64，原有boundary2560上下文、证据顺序、E编号不变。使用原先18个答案要点，不读取99题测试内容、标签或模型答案构造提示。

生成qwen3.7-flash，temperature=0，top_p=1，seed=20260921，max_tokens=1200，JSON输出、关闭thinking。各条件相同上限，但提示长度及实际Token不同，必须报告实际用量。每题3次物理调用，共最多30次，逻辑上每个复查方案含初稿+复查两次。两个复查分支交替先后提交。分两次worker会话，每个最多15次；无重试，无pass@3，无检索、Embedding或Rerank。

准备阶段验证既有冻结文件、脱敏内容与基线提示。运行前冻结代码、协议、配置、初稿请求、复查模板、原rubric；复查请求在保存初稿后确定，发送前落盘，保存父初稿和完整提示摘要。不将rubric或正确答案发给生成模型。密钥只在原Docker worker内读取并保留在内存。

遇到鉴权、额度、配置、worker协议错误立即停止；两个连续提供商失败也停止。初稿无法解析则跳过两个依赖分支，保留失败记录及每种方案10题分母。原句不匹配的初稿仍可复查，以观察修复引用能力。不得看到输出后修改提示重跑。

## 评分及结论规则

沿用generation_report.score_record：独立检查answer正文的18个要点、额外事实错误、是否忠实于上下文、事实是否在claims内、引文是否存在且语义支持。主指标是完整且有依据的回答题数；同时报告完整答案、正确要点、引用有效率、失败与回退。引用字面匹配是自动检查，答案与引用语义由助手逐题复核，不能称独立人工验收。

coverage格式/引用ID检查单独记录，不替代最终答案评分，也不能凭模型标记repaired就计作修复。统计初稿→各分支以及普通→子问复查的实际新增/退步题。耗时与Token报告单次阶段和含初稿的逻辑方案两种口径，实际总账中初稿只计算一次。

预先决策：只有子问复查完整有据题数高于普通复查且没有完整有据退步，才支持扩大开发侧验证；其余结果暂不采用。无论结果怎样，10题都不足以直接替换默认方案。该诊断集经过多轮使用，且先前已有9/10表现，存在天花板及开发选择偏差；单次运行不能证明稳定性、统计显著性或全库效果，更不能把它与99题结果相减当作算法提升。要做最终确认需新增独立政策组评测。
